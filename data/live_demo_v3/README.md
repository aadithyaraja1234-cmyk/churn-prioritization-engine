# Live-demo dataset library — v3 (10k+ rows, clears both sufficiency floors)

> **SAMPLE/DEMO DATA — not real company data.** Every company name,
> customer ID, and value in this folder is synthetic, generated by
> [`scripts/generate_live_demo_v3_batch.py`](../../scripts/generate_live_demo_v3_batch.py)
> from a fixed random seed. None of these three companies exist. Do not
> treat any of this as real customer, financial, or business data.

Distinct from **`data/live_demo/`** (the first 6-company batch) and
**`data/live_demo_v2/`** (the naming-convention stress batch) — both of
those batches are, by design, sized *below*
`src/onboarding/validation.py`'s `MIN_RECOMMENDED_ROWS` (5,634) floor, so a
live demo of either one always hits the non-blocking "results may be less
reliable" acknowledgment step. This batch exists for the opposite reason:
**every company here clears 10,000+ rows**, comfortably above that floor,
so a live demo can show the validation step passing clean, for once, with
no warning to click past. Column naming is ordinary snake_case throughout
(like `data/live_demo/`, not `data/live_demo_v2/`'s deliberate naming-
convention stress test) — row count is the point of this batch, not the
column names.

Nothing in this folder has been registered as a company, uploaded, or
trained by generating it — **generate-and-save only**, same as the other
two batches. Regenerate all three deterministically with:

```
python scripts/generate_live_demo_v3_batch.py
```

## Upload-security check: every cell verified against the real formula-injection guard

`src/onboarding/upload_security.py`'s `read_and_validate_upload()` rejects
any uploaded cell whose stripped value starts with `=`, `+`, `-`, or `@` (a
spreadsheet-formula-injection risk if the file is later opened in Excel/
Sheets) - including a plain negative number like `-42`, not just an actual
formula. This is checked on the raw upload text itself, so it's a real
constraint independent of column mapping or training - a column design
that looks fine in `prepare_and_train()` (which never goes through the
upload endpoint) can still fail the instant someone actually uploads it
through the UI. `vertex-cloud-software.csv`'s `nps_score` was originally
generated on the standard -100..100 NPS range, which meant roughly half
its rows had a value starting with `-` and would have been rejected on
real upload - caught and fixed by generating it on 0..100 instead. Every
file in this batch is now verified, cell-by-cell, against this exact same
check (mirrored as `FORMULA_INJECTION_PREFIXES` in
`scripts/generate_live_demo_v3_batch.py`, asserted in `main()` on every
regeneration) - zero violations across all three files.

## What this batch is for (and isn't)

This is an **offline pre-check only** — generate, check sufficiency, check
real training/gating — not a registration or training run. Nothing here
has a company row, an uploaded file under `data/tenant_uploads/`, or a
`models/<tenant>/` directory. The actual register → upload → map →
validate → train flow happens live, by a person, choosing whichever of
these three best fits the moment — same as `data/live_demo/`'s own
workflow. Because column names here are ordinary and unambiguous (unlike
`data/live_demo_v2/`), expect the mapping step's auto-suggestions to land
correctly for most columns, with the usual plan/tier column needing a
manual "feature" confirmation (there's no "segment" role — see above).
