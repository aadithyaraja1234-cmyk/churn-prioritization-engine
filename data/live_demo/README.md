# Live-demo dataset library

> **SAMPLE/DEMO DATA — not real company data.** Every company name,
> customer/member/client ID, and value in this folder is synthetic,
> generated by
> [`scripts/generate_live_demo_batch.py`](../../scripts/generate_live_demo_batch.py)
> from a fixed random seed. None of these six companies exist. Do not treat
> any of this as real customer, financial, or business data.

Distinct from **`data/test_onboarding_samples/`** (deliberately shows the
onboarding pipeline's *full range* - thin data, confusing column names,
quiet data-quality rot, a malicious upload - so an engineer can see every
failure mode) and **`data/raw/`** (Telco/Banking's committed, permanently
guarded reference data). This folder exists for one purpose: **live,
in-person manual demonstration**. Every file here is deliberately clean -
no injected data-quality issues - and was engineered (and pre-checked
offline, artifacts discarded afterward - see "Pre-check results" below) to
plausibly clear every module's own real sanity gate
(`src/models/tenant_training.py`'s `_run_optional_modules()`/
`_sanity_check()`) if registered/uploaded/mapped/validated/trained through
the actual onboarding UI - which is a **manual, live step done by a
person, on demand**, not something this repo does for you. Nothing in
this folder has been registered as a company, uploaded, or trained by
generating it.

Regenerate all six deterministically with:

```
python scripts/generate_live_demo_batch.py
```

## Why each tier/contract/plan column is spelled the way it is

`src/features/encode.py` encodes every categorical covariate as a plain
integer code in **alphabetical** order, and `survival.py` fits that code
as an ordinary linear Cox covariate. A tier column whose alphabetical
order doesn't match its true risk order gets its real signal washed out
by whatever continuous, tier-correlated column (almost always revenue) is
fit alongside it - verified directly against `lifelines.CoxPHFitter`
before committing to this approach: a symmetric "Basic=highest risk,
Premium=lowest, Standard=middle" design, encoded alphabetically as
Basic=0/Premium=1/Standard=2, fit a hazard ratio within 2% of 1.0 despite
a large designed effect. Every tier/contract/plan label below was chosen
so its **alphabetical order already matches its intended risk order**
(highest-risk name sorts first) - the same coincidence Telco's own real
`Contract` column already has ("Month-to-month" < "One year" < "Two
year", both alphabetically and by risk). That's why Aurora's mid-tier is
"Plus" and not "Standard", Northgate's plans are "Flex/Standard/Term" and
not "Month-to-month/1-Year/3-Year", and so on - not arbitrary naming, a
deliberate fix for a real mechanism.

## Pre-check results (offline, throwaway artifacts, not a persisted run)

Every file below was run through the *actual* project code
(`src.models.tenant_training.prepare_and_train()` - the same function the
real training endpoint calls) once, against a throwaway tenant id, purely
to verify it would clear every module's real sanity gate - **no database
row was ever created and every model artifact was deleted immediately
after**, so nothing here has been "pre-trained" for your live demo; you'll
see the real training run happen when you do it.

|---|---:|---|---|---|---:|
| `aurora-streaming.csv` | 0.784 | 0.832 (`subscription_tier` HR 0.34) | 0.128 / 49% | 5.0% | 0.497 |
| `palisade-fitness.csv` | 0.744 | 0.844 (`membership_tier` HR 0.25) | 0.166 / 70% | 5.0% | 0.655 |
| `northgate-broadband.csv` | 0.782 | 0.839 (`contract_length` HR 0.18) | 0.133 / 63% | 5.0% | 0.523 |
| `solstice-media.csv` | 0.723 | 0.755 (`plan_level` HR 0.52) | 0.124 / 55% | 5.0% | 0.509 |
| `ferrous-vale-wealth.csv` | 0.743 | 0.765 (`portfolio_tier` HR 0.27) | 0.197 / 79% | 5.0% | 0.727 |

All comfortably inside every module's real sanity range
(`src/models/tenant_training.py`): classifier ROC-AUC in (0.55, 0.98),
survival c-index in (0.55, 0.95), segmentation silhouette > 0.05 with no

exactly at the 5% contamination target), CLV R² > 0.05. In every file the
intended tier/contract/plan column is, by a wide margin, the categorical
covariate the fitted Cox model relies on most (hazard ratio furthest from
1.0) - confirming the alphabetical-ordering design above actually worked,
not just in theory.

## Data-sufficiency check: an honest, expected warning on every file

`src/onboarding/validation.py`'s two thresholds:

- `MIN_RECOMMENDED_ROWS` = 5,634 (Telco's own real training-row count)
- `MIN_RECOMMENDED_FEATURES` = 8 usable mapped feature columns

Every file here comfortably clears the feature-richness floor (**10**
usable feature columns each, +2 margin) but **none clears the row-count
floor** - by design: rows were sized per-company for narrative realism
(Northgate's 800 "fewer, larger B2B accounts" and Ferrous Vale's 1,200
"long-relationship wealth management" are deliberately smaller than a
mass-market consumer subscription's row count, the same way a real
company that size would be), not to chase 5,634. This is the same
**non-blocking** "thin data" warning `RUNNING.md` and
`data/test_onboarding_samples/company_harborline_insurance.csv` already
document elsewhere in this project: `can_proceed` stays `true`, and the
onboarding wizard's validation report will show a "results may be less
reliable" acknowledgment step to click through - not a rejection. Expect
to see and click past it live, for all six.
