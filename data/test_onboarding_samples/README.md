# Onboarding pipeline demo datasets

> **SAMPLE/DEMO DATA — not real company data.** Every company name, customer
> ID, and value in this folder is synthetic, generated by
> [`scripts/generate_onboarding_samples.py`](../../scripts/generate_onboarding_samples.py)
> from a fixed random seed. None of these five companies exist. Do not treat
> any of this as real customer, financial, or business data.

These five files exist to show the onboarding pipeline's range end-to-end -
from a clean upload that sails through, to thin data, to confusing column
names, to quiet data-quality rot, to an outright malicious upload. Each one
is a distinct, named fictional company so the demo tells a story instead of
reading like generic test fixtures. Regenerate all five deterministically
with:

```
python scripts/generate_onboarding_samples.py
```

---

### Meridian Wireless — `company_meridian_wireless.csv`

A five-year-old regional wireless carrier competing against the national
players on network reliability in mid-size metro markets. Meridian's billing
and CRM stack has been stable since launch, so their customer export is
exactly what a well-run telecom's data team would hand over on day one:
6,000 customers, 21 columns spanning contract terms, service add-ons, and
billing history, zero missing values. This is the "everything works" path -
a real onboarding demo needs at least one company where the pipeline just
says yes.

### Harborline Insurance Partners — `company_harborline_insurance.csv`

A small independent regional insurance agency - a handful of agents, a
few thousand policyholders, and a legacy policy-management system that was
never built to export anything beyond the bare minimum. When asked for a
churn dataset, Harborline's office manager exported the only three fields
she could easily get to: a policyholder ID, the annual premium, and whether
the policy lapsed. It's real, usable data as far as it goes - there just
isn't much of it, in either rows (200) or columns (3).

### Fernwood Retail Collective — `company_fernwood_retail.csv`

A co-op of independent boutique retailers that share a single loyalty and
subscription-box platform, homegrown by a small internal engineering team
over several years without much appetite for renaming things once they
shipped. The data is every bit as rich as Meridian's (same 6,000-row,
21-column shape) - it's just labeled in Fernwood's own internal shorthand
(`cust_ref`, `mo_bill_usd`, `left_us`) instead of anything an outside system
would recognize on sight. A good onboarding flow should handle this by
asking, not guessing.

### Cobalt Health Network — `company_cobalt_health.csv`

A regional health-plan network mid-way through a multi-year migration off a
legacy claims system onto a new one. The export script pulling from the new
system is still being debugged: several columns are 27-29% null where a
join is silently failing, a couple of others (`PaperlessBilling`,
`OnlineSecurity`) are populated in every row but with a migration script's
hardcoded default rather than each member's real value. The column count
looks perfectly fine at a glance - the problem only shows up once you check
whether each column actually carries usable signal.

### Redline Motors Direct — `company_redline_motors.csv`

An auto dealership group's customer-retention data, exported by someone who
pasted a few stray values into their spreadsheet before saving as CSV -
including, in a handful of cells, values that Excel and Google Sheets would
interpret as formulas rather than data (`=cmd|'/c calc'!A1`, `+1+1`,
`@SUM(1,1)`, `-2+3`). Whether that was an honest mistake or a deliberate
probe doesn't matter to the pipeline: this file exists to show what happens
when a formula-injection payload reaches the upload endpoint - it gets
rejected outright, with a specific reason, before mapping or validation ever
runs. See the live walkthrough writeup for the actual rejection response.

## What each file is expected to demonstrate

| File | Rows | Cols | Expected result |
|---|---:|---:|---|
| `company_meridian_wireless.csv` | 6,000 | 21 | Green "Ready to go" - clean data, high feature richness |
| `company_harborline_insurance.csv` | 200 | 3 | Amber "Needs attention" - both row-count AND feature-richness warnings |
| `company_fernwood_retail.csv` | 6,000 | 21 | Mapping step requires manual confirmation on ~4 columns (no auto-suggestion, or a wrong low-confidence one); green once correctly mapped |
| `company_cobalt_health.csv` | 6,000 | 21 | Amber "Needs attention" - row count is sufficient, but nulls/constant columns drop usable features to 5 (below the 8 floor) |
| `company_redline_motors.csv` | 2,000 | 21 | Rejected at upload - never reaches mapping or validation |

A note on Meridian's row count: the task this was built from suggested
"~2,000 rows" for Meridian, but this system's real row-count threshold
(`MIN_RECOMMENDED_ROWS` in `src/onboarding/validation.py`) is 5,634 - the
actual training-row count of the real Telco reference model. 2,000 rows
would trip the row-count warning and never produce the clean "Ready to go"
verdict this file is meant to demonstrate, so Meridian (and Fernwood and
Cobalt, for the same reason) use 6,000 rows instead.
